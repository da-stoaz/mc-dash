# Bug audit — 2026-10-28

Reviewed commit: `25600cfc0e45145843d92c2b6f5d6cc6bddd5fe2` on
`codex/server-permissions-and-memory-limits`. The commit was pushed before this
review. These findings are **not fixed** by that commit.

## Fixes following the audit

All nine reproduced findings below have fixes and regression coverage in this
branch. Rebuilds stage the replacement, preserve existing worlds over ZIP content,
and restore the previous pack on caught failures. Interrupted publication retains
the previous copy and blocks starts until recovery. Snapshot failures always
attempt to re-enable autosaves and report unconfirmed flush/recovery as failures.
Descriptor-relative filesystem operations prevent parent-path redirection and
write complete configurations atomically. Python 3 is included in the backend image
and is required for local development; no Python packages are needed.

Settings, lifecycle actions and snapshot creation now share mutation locks.
Production RAM edits use the verified shared pool instead of legacy reservation
sums. Long actions, imports, restores and settings changes can return persistent
operation IDs, which the dashboard polls. Backend restarts mark unfinished jobs as
failed without replaying them. ZIP decompression runs in a worker thread so it
cannot block API status polling or the Minecraft router.

Rebuild staging needs temporary disk space for a replacement pack and copied worlds
unless the filesystem can reflink them. The old installation remains intact if
copying fails. Docker recreation itself is not transactional: after a Docker error,
a rebuild retry may still be required even though the old files were restored.

Validation completed locally: 328 backend tests, 33 browser tests, backend build,
frontend TypeScript check, and 49 targeted tests in the rebuilt Linux backend
image. The Linux tests include real root-to-container UID/GID ownership and write
checks; six Python filesystem fault/race probes run inside the file-helper test.
Production was not accessed or upgraded.

The sections below retain the original reproduction evidence for review.

The review used disposable local data directories, actual preparation/config
functions with Docker creation stubbed, route handlers with controlled service
responses, a loopback fake RCON server, and an isolated production frontend
Docker image. No production services or worlds were accessed. The normal test
suite passing does not cover these failure cases.

## P1: Rebuild deletes nested and custom-named worlds

Location: `backend/src/services/prepareService.ts:30` (`cleanPackDir`).

Only immediate `pack/world`, `pack/world_nether`, and `pack/world_the_end`
directories survive cleanup. The application supports nested pack working
directories, but rebuilding a pack containing `bundle/start.sh` deleted an
existing `pack/bundle/world/level.dat`. A separate fixture with
`level-name=myworld` also lost `pack/myworld/level.dat`.

Resolve the actual old working directory and world configuration before changing
the pack. Preserve all world data independently of the extraction directory;
do not infer it solely from three hardcoded folder names.

## P1: Pack extraction overwrites the world that cleanup preserved

Location: `backend/src/services/prepareService.ts:648` and `:760`.

Cleanup puts the preserved world back before `extractAllTo(packDir, true)`.
Rebuilding with a ZIP containing `world/level.dat` replaced the fixture's current
progress with the older contents supplied by the ZIP.

Extract into a separate staging directory and keep existing saves authoritative.
World preservation must cover the extraction step, not just cleanup.

## P1: A partial RCON failure leaves Minecraft autosaving disabled

Location: `backend/src/services/snapshotService.ts:109` and `:126`.

The snapshot code sends `save-off` and `save-all flush` together, but only sends
`save-on` if the complete sequence succeeds. The actual RCON client was exercised
against a fake TCP server that acknowledged `save-off` and disconnected on
`save-all flush`. Snapshot creation reported success; the observed commands were
only `save-off`, `save-all flush`, and autosaving remained disabled in the fixture.

Always attempt to restore autosaving after attempting to disable it, including
partial command failures. Surface a failed re-enable attempt, and distinguish an
unflushed live backup from a confirmed consistent snapshot.

## P1: Parent-directory replacement bypasses the new file-write boundary

Location: `backend/src/services/serverFiles.ts:89` and `:90`; the ownership helper
also checks a pathname separately from opening it.

`O_NOFOLLOW` protects the last path component only. A deterministic race probe
renamed the validated parent directory and replaced it with a symlink immediately
before `fs.open`. `writeServerFile` then overwrote a file outside the managed
server directory. All targets were disposable fixture files.

This is relevant to a running container that can rename directories under its
writable `/server` mount while the root backend applies configuration. Static
symlink rejection tests do not exercise this race. The probe demonstrates the
filesystem primitive, not a complete remote exploit.

Use directory-descriptor-relative operations with containment enforced at open
time, or an equivalent design that prevents a Minecraft-controlled parent from
redirecting privileged writes/ownership changes. Another pathname precheck alone
does not close the race.

## P2: An invalid pack destroys the working installation before validation

Location: `backend/src/services/prepareService.ts:760`.

`cleanPackDir` runs before the ZIP is opened and validated. With an invalid ZIP,
preparation threw `Invalid or unsupported zip format`, but the existing launcher
had already been deleted. There is no rollback of the working pack.

Validate and prepare the replacement separately, then switch it into place only
after success. Keep the old installation available on extraction, configuration,
dependency, and image preparation failures.

## P2: Long operations fail at the frontend after 30 seconds

Location: `frontend/next.config.ts:16` and `:18`; installed Next proxy implementation
defaults `proxyTimeout` to 30,000 ms.

An isolated production frontend container proxied a disposable backend request
that needed 35 seconds. It returned HTTP 500 after 30,012 ms with `ECONNRESET`.
Preparation, large ownership repairs, and snapshot operations can exceed this
window. The browser sees failure while the backend operation may still continue.

Prefer background jobs with status polling for long operations. Make timeout and
retry behavior explicit so a disconnected request cannot encourage duplicate
mutations. Increasing a proxy timeout alone does not cover upstream proxy limits.

## P2: RAM edits still use legacy reservation admission with the pool enabled

Location: `backend/src/routes/servers.ts:606` and `:623`.

Start admission bypasses legacy estimates when the shared pool is enabled, but
the PATCH resource path does not. A route probe with pool enforcement enabled,
2,000 MiB current usage in a 12,000 MiB pool, and exhausted legacy peak allowances
rejected a 6,000 → 6,500 MiB server-cap edit with `MEMORY_BURST_EXCEEDED`.

This probe supplied the capacity response; it did not allocate real RAM. It
confirms that the edit path uses the obsolete gate independently of pool usage.
Use one coherent pool-aware policy for both starts and resource edits, retaining
appropriate host-pressure and live-limit safeguards.

## P2: Configuration edits bypass the lifecycle lock

Location: `backend/src/routes/servers.ts:588` and the recreation branch at `:776`.

The PATCH handler does not consult `lifecycleBusy`. A route probe marked a stopped
server busy (the state used while restoring), then changed its Java image. The
handler returned HTTP 200 and invoked container recreation while the lock was
still held. Configuration writes and recreation can therefore interleave with a
restore or rebuild touching the same files.

Serialize configuration mutations that touch server files or containers with
the existing lifecycle operations. Status checks alone are insufficient.

## P2: A failed configuration write destroys the previous file

Location: `backend/src/services/serverFiles.ts:97`.

The helper truncates the existing file before writing the new contents. Injecting
an `ENOSPC` error at the write left an existing configuration file empty. This
affects properties, JVM arguments, access lists, and generated scripts using the
helper. The test simulates disk exhaustion; it does not fill the host disk.

Write a temporary file completely, apply the required ownership, and replace the
destination atomically using the same secure directory containment strategy as
the parent-directory race fix. Failure must preserve the previous contents.

## Scope and next work

The current changes address these nine findings. Validate the rebuilt deployment
image before rolling them out; this audit and its local regression checks are not
a production deployment or an exhaustive security assessment.

This is a targeted review of preparation/rebuild, permissions, configuration,
snapshots, proxying, lifecycle coordination, and RAM admission, not a claim that
all remaining application code is bug-free.
